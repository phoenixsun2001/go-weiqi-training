# 围棋棋力训练应用 — 设计文档

- **日期：** 2026-06-20
- **状态：** 待评审
- **作者：** ZCode（与用户协作）

## 1. 目标与成功标准

**产品目标：** 创造一个桌面围棋训练应用，能根据用户当前棋力水平进行针对性强化训练与对战练习，用高效、科学的方法帮助业余 1 段（约 1d）以上水平的棋手快速提升到业余 5 段（约 5d）或以上。

**成功标准：**

1. 桌面应用可在 Windows（首要）/ macOS / Linux 运行，调用本地 KataGo 引擎进行推理。
2. 包含四大训练模块：
   - **AI 复盘分析**（胜率曲线、选点、失误标记）
   - **针对性题库训练**（按棋力弱点动态出题、错题本）
   - **可调难度对战**（AI 对手模拟指定段位）
   - **猜棋 / 复盘训练**（猜下一手并与 AI 推荐对比）
3. 具备基于 Elo/Glicko 的棋力评估与跟踪，并据此驱动"针对性"训练。
4. 完全离线可用（本地 KataGo + 本地 SQLite 存储），无强制云端依赖。
5. 对局记录、评级历史、题库进度持久化保存。

**非目标（本阶段）：** 云端账号同步、在线对战匹配、移动端、付费商业化。

## 2. 技术决策（已与用户确认）

| 维度 | 决策 | 理由 |
|---|---|---|
| 平台 | 桌面应用 | 本地 GPU 推理性能最强，适合高强度训练 |
| 技术栈 | **Tauri 2 + Rust 后端 + React/TS 前端** | 包体小、内存低、Rust 稳定管理长时分析任务 |
| AI 引擎 | **KataGo**（GTP 协议） | 棋力顶尖、可调难度、输出胜率/策略用于复盘 |
| 棋力评估 | **Elo/Glicko 对战胜率跟踪** | 简洁有效，MVP 够用，后续可叠加棋谱失误率 |
| 范围 | 四模块全量交付 | 复盘 / 题库 / 对战 / 猜棋 一次到位 |
| 存储 | 本地 SQLite | 离线优先，无云端依赖 |

## 3. 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    桌面应用 (Tauri 2)                          │
│                                                               │
│  ┌─────────────────────── 前端 (React + TS) ──────────────────┐│
│  │  棋盘渲染 (Canvas/WebGL)  │  复盘/胜率图  │  对战/题库 UI   ││
│  │  路由: 对战 / 复盘 / 题库 / 猜棋 / 棋力面板                ││
│  └──────────────────────────────┬──────────────────────────────┘│
│                       Tauri IPC (invoke + events)              │
│  ┌──────────────────────────────┴──────────────────────────────┐│
│  │                  后端 (Rust)                                ││
│  │  ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐    ││
│  │  │ Engine Mgr  │  │  Game State  │  │  Rating Service   │    ││
│  │  │ (KataGo进程) │  │  (SGF/规则)   │  │  (Elo/Glicko)    │    ││
│  │  └──────┬──────┘  └──────────────┘  └──────────────────┘    ││
│  │         │                                                    ││
│  │  ┌──────┴────────────────────────────────────────────────┐ ││
│  │  │  KataGo GTP 子进程  (分析引擎 / 对手引擎,可配多实例)    │ ││
│  │  └────────────────────────────────────────────────────────┘ ││
│  │  ┌─────────────┐  ┌──────────────┐  ┌──────────────────┐    ││
│  │  │ Problem DB  │  │  Local Store │  │  Review Pipeline │    ││
│  │  │ (题库 SGF)  │  │  (SQLite)    │  │  (胜率/失误分析)  │    ││
│  │  └─────────────┘  └──────────────┘  └──────────────────┘    ││
│  └──────────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────────┘
```

**核心架构决策：**

1. **双 KataGo 进程角色** — 一个"分析引擎"（深度思考、输出胜率/策略/选点，用于复盘和猜棋），一个"对手引擎"（受限思考、模拟指定段位，用于对战）。互不阻塞，复盘时可同时下棋。
2. **`game_state` 单一事实源** — Rust 侧维护当前棋局状态（落子序列、提子、劫、贴目、数子规则）。所有模块（对战/复盘/猜棋）都从它派生视图。前端只渲染、不持有规则逻辑。
3. **本地 SQLite 存储** — 用户档案、对局记录、Elo 历史、题库进度、错题本。完全离线，无云端依赖。
4. **IPC 用事件流** — KataGo 分析是长时间任务，通过 Tauri events 推送增量结果（每步胜率），而非前端轮询。

## 4. 核心组件与职责划分

### 4.1 Rust 后端

每个组件单一职责、可独立测试。

| 组件 | 职责 | 依赖 |
|---|---|---|
| `engine_manager` | 启停 KataGo 子进程、GTP 协议收发、管理"分析"与"对手"两类实例 | KataGo 二进制 |
| `game_state` | 棋局规则（落子/提子/劫/数子/贴目）、SGF 读写、坐标转换 | 无（纯逻辑） |
| `rating_service` | Elo/Glicko 评级计算、对局结果记录、棋力历史曲线 | `rusqlite` |
| `review_pipeline` | 调分析引擎逐手评估、计算胜率曲线、标记失误/疑问手 | `engine_manager`, `game_state` |
| `problem_db` | 题库（SGF/JSON）加载、按类型/难度检索、错题本 | `rusqlite` |
| `opponent_ai` | 按目标段位限制 KataGo 思考（visits/搜索时间/随机性），生成对手落子 | `engine_manager`, `game_state` |
| `local_store` | SQLite 持久化（用户档案、对局、评级、题库进度） | `rusqlite` |
| `tauri_commands` | 对前端暴露的 IPC 命令与事件（`#[tauri::command]`） | 上述全部 |

### 4.2 前端（React + TS + Zustand/Redux）

| 模块 | 职责 |
|---|---|
| `Board` | Canvas/WebGL 棋盘渲染、落子动画、坐标/标记层 |
| `WinRateChart` | 复盘胜率曲线（D3/Recharts），点击跳转到对应手 |
| `GameView` | 对战主界面（棋盘 + AI 信息面板 + 设置） |
| `ReviewView` | 复盘界面（棋盘 + 胜率图 + 选点分析 + 变化图） |
| `ProblemView` | 题库练习（题目棋盘 + 作答 + 解析） |
| `GuessView` | 猜棋界面（隐藏下一手，作答后对比） |
| `RatingPanel` | 棋力面板（当前 Elo、历史曲线、训练建议） |

## 5. 数据流（四大模块）

### 5.1 可调难度对战

```
用户落子 → game_state 推进 → opponent_ai 按目标段位调参请求 KataGo
→ KataGo 返回选点 → 更新棋局 → 终局 rating_service 更新 Elo → 存入 local_store
```

**段位模拟机制：** 通过限制 KataGo 的 `maxVisits` / 思考时间 / 加入策略网络的随机性（`noise`/`temperature`）来模拟从业余 1 段到职业的不同强度。目标段位由 `rating_service` 推断（略高于用户当前 Elo，形成"跳一跳够得着"的训练强度）。

### 5.2 AI 复盘分析

```
加载 SGF（外部导入或本地对局）→ review_pipeline 逐手向"分析引擎"
发 kata-analyze/lz-analyze → Tauri events 增量推送每手胜率与最佳选点
→ ReviewView 绘制胜率曲线、标红失误手
（失误判定：用户选点 vs 最佳点胜率损失 > 阈值，默认 3%）
```

### 5.3 针对性题库训练

```
problem_db 按 rating_service 给出的弱点（如官子弱）+ 难度过滤出题
→ 用户作答 → 比对正解 → 记入错题本 → 动态调整后续出题权重
```

**弱点推断：** 初版按复盘失误类型统计（布局/中盘/死活/官子）作为弱点标签；题库按标签 + 难度匹配。

### 5.4 猜棋 / 复盘训练

```
选定职业/强 AI 棋谱 → 用户猜下一手 → 揭晓后与 AI 推荐对比
→ 胜率差作为评分（落在 AI top-N 候选内得分高）
```

## 6. 错误处理

- **KataGo 进程崩溃/未安装**：启动检测 + 友好引导（下载/路径配置向导）；运行中崩溃自动重启并恢复 `game_state`。
- **GPU 不可用**：降级到 CPU 后端，UI 明确提示"性能受限"，降低默认分析并发。
- **长时间分析可取消**：所有 GTP 命令带超时与取消令牌；前端可中断。
- **棋谱导入校验**：非法 SGF/坐标拒绝并提示原因；贴目/规则冲突时让用户确认。
- **数据完整性**：SQLite 用事务包裹评级更新与对局记录；定期本地备份。

## 7. 测试策略

- **`game_state`（规则核心）**：单元测试覆盖落子/提子/劫/双活/数子，含经典死活与终局判定用例。
- **`rating_service`**：单元测试验证 Elo 变动、预期胜率、段位映射边界。
- **`engine_manager`**：用假 GTP 进程（脚本回放固定应答）测试协议解析与异常。
- **`review_pipeline`**：用录制好的 KataGo 输出夹具，验证胜率曲线与失误标记逻辑。
- **端到端**：Tauri 集成测试跑通"导入棋谱→复盘→存评级"主流程（用 mock 引擎）。
- **前端**：Board 渲染快照测试；各 View 组件测试（mock IPC）。

## 8. 交付阶段（实现计划锚点）

虽然本阶段为四模块全量，但实现按依赖顺序推进（writing-plans 阶段细化）：

1. **脚手架** — Tauri 2 + Rust 后端 + React 前端骨架；项目结构；SQLite 初始化。
2. **引擎集成** — `engine_manager` 接入 KataGo GTP；启动检测与降级。
3. **规则核心** — `game_state`（落子/提子/劫/数子/SGF）+ 单元测试。
4. **MVP 模块 A：可调难度对战** — `opponent_ai` + `GameView` + `rating_service`。
5. **MVP 模块 B：AI 复盘分析** — `review_pipeline` + `ReviewView` + `WinRateChart`。
6. **模块 C：针对性题库** — `problem_db` + `ProblemView` + 弱点推断。
7. **模块 D：猜棋训练** — `GuessView` + 评分逻辑。
8. **棋力面板与收尾** — `RatingPanel`、打包发布、文档。

## 9. 开放问题（实现阶段解决）

- KataGo 权重文件与二进制的分发方式（首次启动下载 vs 随应用打包）。
- 段位 ↔ Elo ↔ KataGo `maxVisits` 的精确校准映射（需实测调参）。
- 题库内容来源（自有/开源 SGF 题库导入）。
- macOS/Linux 的 GPU 后端差异（OpenCL/Metal/CUDA）。
